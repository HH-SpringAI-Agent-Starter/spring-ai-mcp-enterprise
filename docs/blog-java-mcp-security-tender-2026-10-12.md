## 二、10 月第二周，MCP 安全漏洞集中爆发

如果把近一周的 CVE 摊开，会看到一个反复出现的模式：

| CVE | 日期 | 严重度 | 一句话 |
|-----|------|--------|--------|
| CVE-2026-108585（argocd-mcp 路径穿越删 K8s） | 10-10 | 5.4 | MCP 工具绕过底层 RBAC |
| CVE-2026-108586（@1mcp/agent 越权） | 10-10 | 5.4 | 低权客户端调别人 scope 工具 |
| JeecgBoot 任意用户读 MCP 密钥 | 10-10 | 7.1 HIGH | 权限检查被注释掉 |
| x64dbg-MCP 任意网络客户端跑调试器 | 10-09 | 9.3 CRITICAL | 无认证暴露全功能 |
| mcp-go 1.2.1 无界读取 OOM | 10-11 | 8.7 HIGH | 9.1k stars 主导 Go 实现，发布两天即被报 |
| Splunk MCP Server 反序列化 RCE | 10-08 | 9.1 CRITICAL | 凭据组件反序列化未校验 |

安全研究者给这类缺陷下了精准论断：**"MCP server 把客户端认证当成了工具级授权"**——这是结构性弱点类，不是单点 bug。WorldofAI 统计在录 AI CVE 已达 **729 个**（111 关键 / 352 高 / 5 个 CISA KEV）。

**结论**：凡是"成熟产品长出 MCP 面，权限模型默认不带过来"的地方，都需要一层**独立的治理平面**。

## 三、本框架的定位：Spring AI Alibaba 的"治理增强层"

Spring AI Alibaba 已是 Java Agentic 事实标准（11k stars、275 contributors、内置 Multi-Agent + Nacos A2A + MCP 管理）。但评测机构 FollowAgents 直指其 **"1 safety controls not found"（缺安全控制）**。

我们的 `spring-ai-mcp-enterprise` 不做重复造轮子，而是补上最缺的那层：

- **mcp-governance**：T0–T4 风险分级 + 工具级 Scope-ACL + HITL 人类在环 + JDBC 审计（SIEM 可对接）+ 限流 + fail-closed
- **mcp-auth**：Bearer 强制校验 + jti 防碰撞 + RFC 7009 吊销端点
- **mcp-registry / mcp-gateway**：Nacos+Higress 同款"注册中心 + 网关"定位，联邦工具命名空间隔离
- **mcp-tenant**：多租户 Row/Schema/实例三级隔离，直接对齐等保三级

一句话：**Spring AI Alibaba 解决"能不能跑"，我们解决"稳不稳、值不值、合不合规"。**
