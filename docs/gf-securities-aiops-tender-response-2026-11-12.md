## 3. 为什么 13327 应该关心「注册中心自己」（本期最有说服力的一段）

11-11 AWS 官方两份公告（`2026-179-AWS` / `2026-180-AWS`）证明：**把一堆存量平台封装成 MCP 工具并集中注册之后，注册表会变成最高价值攻击目标**。

- `CVE-2026-100307`(8.8)：管理 API 只认证不授权 → 低权限用户把自己 IdP group 映射成 `mcp-registry-admin`，管理员身份按请求派生、下次请求生效，可读走**注册时存的各平台凭据与自定义 header**。
- `CVE-2026-125926`(8.5)：注册 / 修改 API 可把上游指向内网与云元数据 → 对运维场景尤其致命，因为**可观测 / 日志 / 自动化平台本来就在内网**。
- 官方修复明确：**升级前已存配置不变、已植入映射不撤销、已泄露凭据不失效** → 必须逐个复验所有已注册平台的上游地址。

对应到 13327 的场景：封装的是**内网运维平台**，一旦上游地址可被改写，攻击面直接落在生产运维系统。因此「目标 7」不能只答「我们支持 MCP 封装」，必须答「**封装之后怎么管住注册表、怎么证明存量干净**」。完整 12 项验收清单见 [`registry-control-plane-self-defense-2026-11-12.md`](registry-control-plane-self-defense-2026-11-12.md)。

## 4. 买方必问 5 问

| 买方问法 | 答法 |
| --- | --- |
| 「你们是运维平台原厂吗？」 | 不是。我们是**治理增强层技术分包**，主体须由满足资质的广州本地集成商承担；我们不碰调用图 / 知识图谱 / 运维技能本体。 |
| 「封装 MCP 会不会让内网运维平台更危险？」 | 会，如果只做封装不做准入。所以我们把上游 SSRF 准入、管理面授权、存量复验、本地监听器六道闸做成**可现场跑的验收**，而不是写在方案里。 |
| 「已有平台要不要改造？」 | 不要。复用存量权限与审计体系，在外面加治理层 —— 这也是 11-12 OnePlan 官方稿「respects existing OnePlan permissions」的同一思路。 |
| 「DAU/WAU 从哪来？」 | 审计埋点契约按 caller / tool / skill 维度出字段；⚠️ 当前 `mcp_security_*` 在 `examples/` 层，**`mcp-monitor` 主模块尚未内置导出**，接入工作量要如实计入排期。 |
| 「有没有金融案例？」 | **没有**。本项目无商业合同 / 中标 / 金融案例 / 等保测评，只能以技术分包与可运行验收证据参与，不虚构材料。 |
