# V1.22 发布说明 —— Skill Registry 持久化（JDBC）：重启/滚动发布后版本治理状态不丢失

> 发布日期：2026-09-11
> 核心主题：把 V1.21 的「纯内存技能注册表」升级为「可持久化的企业治理层」——opt-in 开启，零依赖默认不变
> 版本基线：V1.21（Skill Registry）→ V1.22（Skill Registry + 持久化 / 启动可恢复）

---

## 一、为什么要做 V1.22

V1.21 交付了 Skill Registry（注册 / 语义化版本 / 显式激活 / 故障回滚 / 灰度路由），命中了沃尔玛中国「Skill、Spec Registry 服务」与上海 MCP 平台工程岗的 JD 关键词。但它在设计上是**纯内存**的：所有状态放在进程内 `ConcurrentHashMap`。

这在 demo 里没问题，在企业里有一个致命短板：

| 场景 | V1.21 行为 | 影响 |
| --- | --- | --- |
| 应用重启 / K8s 滚动发布 | 注册表清空 | **灰度权重、当前 ACTIVE 版本全部丢失**，重新部署后每个 Skill 需要人工重新注册 |
| 多副本实例 | 各副本内存互不可见 | 灰色发布只能命中单副本，无法真正做流量治理 |
| 故障回滚（核心卖点） | 重启后 `rollback` 找不到历史版本 | 回滚能力在重启后失效 |

企业级 JD 反复强调的「**版本管理、灰度发布、故障回滚、可监控可复用**」，前提是**状态可持久化**。V1.22 补上这一环。

**设计原则：opt-in、向后兼容。** 默认 `store=memory`，行为与 V1.21 完全一致（零外部依赖，无 DataSource 也能跑）；只有显式配置 `store=jdbc` 时才启用持久化。

## 二、新增内容

### 1. 持久化 SPI：`SkillRegistryStore`（新接口）

把「注册表状态」与「存储介质」解耦，定义 8 个方法：

```java
boolean isPersistent();                 // 是否真正持久化（内存实现返回 false）
List<SkillSpec> loadVersions();         // 全量历史版本
Map<String,String> loadActiveVersions();          // skill -> 当前 ACTIVE 版本
Map<String,Map<String,Integer>> loadGrayWeights();// skill -> version -> 灰度权重
void upsert(SkillSpec spec);            // 插入/更新一个版本
void setActive(String name, String version);
void setGrayWeight(String name, String version, int weight);
void clearGray(String name);
void removeSkill(String name);
```

两个实现：

- **`InMemorySkillRegistryStore`**（默认）：全部 no-op，`isPersistent()=false`。保证 V1.21 的行为零变化。
- **`JdbcSkillRegistryStore`**（V1.22 核心）：单表、方言无关的 JDBC 实现。

### 2. `JdbcSkillRegistryStore`——一张表搞定

```sql
CREATE TABLE IF NOT EXISTS mcp_skill_registry (
  skill_name   VARCHAR(128) NOT NULL,
  version      VARCHAR(64)  NOT NULL,
  description  VARCHAR(1024),
  category     VARCHAR(128),
  owner        VARCHAR(128),
  status       VARCHAR(32),
  input_schema VARCHAR(4000),          -- SkillSpec 的 JSON schema
  active       INT NOT NULL DEFAULT 0, -- 1 = 当前服务版本
  gray_weight  INT,                    -- NULL = 未灰度
  created_at   BIGINT,
  updated_at   BIGINT,
  PRIMARY KEY (skill_name, version)
);
```

工程取舍：

- **只用 `CREATE TABLE IF NOT EXISTS` / `INSERT` / `UPDATE` / `DELETE`**，不用 `MERGE`（各数据库语法差异最大的一条），因此 **H2 / MySQL / PostgreSQL / SQL Server 均可直接运行**。
- **upsert = delete + insert**（绑参），表规模小（几十~几千行），代价可忽略；且 upsert 时会**保留已有行的 active 标记**，不会把正在服务的版本误置为非激活。
- **`active INT` 而非 BOOLEAN**：跨库最稳。
- **`input_schema` 默认 `VARCHAR(4000)`**：所有库都支持；生产若 schema 更大，按指南改为 `TEXT` / `CLOB`。
- 写入全部走 `JdbcTemplate` 绑参，无 SQL 注入面。

### 3. `SkillRegistry` 接入持久化 + `reload()` 热启动

- 新增构造器 `SkillRegistry(props, store)`；旧构造器 `SkillRegistry(props)` 委托到内存实现，**源码级向后兼容**（V1.21 的 12 个测试一行未改仍全绿）。
- 每次 `register / activate / rollback / gray / remove` 在内存变更成功后，**best-effort 落库**：
  - 落库失败只记 `WARN`，**绝不阻断治理操作**（availability over durability，DB 抖动时注册表仍可用）。
- 新增 `reload()`：启动时从存储加载全部版本、ACTIVE 版本与灰度权重，重建内存态。非持久化存储上是 no-op，store 故障则打 WARN 后以空表启动。
- 新增 `isPersistent()` 供上层判断。

### 4. 自动配置：按需装配

`SkillRegistryAutoConfiguration` 新增 `SkillRegistryStore` Bean：

- `store=jdbc` 且容器里存在 `JdbcTemplate` → 装配 `JdbcSkillRegistryStore`，并按 `init-schema` 决定是否建表；
- `store=jdbc` 但**没有 DataSource** → 打印 WARN 后**自动降级为内存**（不会因为少配一个数据源就起不来）；
- 其他情况 → 内存实现。

`SkillRegistry` Bean 创建后若为持久化存储，自动 `reload()`。

### 5. 配置项（`mcp.enterprise.registry.skill`）

```yaml
mcp:
  enterprise:
    registry:
      skill:
        enabled: true
        max-versions-per-skill: 20
        store: jdbc                      # V1.22: memory(默认) | jdbc
        table: mcp_skill_registry        # V1.22
        init-schema: true                # V1.22: 自动建表（Flyway/Liquibase 托管时置 false）
```

## 三、影响与下一步

- **兼容性**：默认行为与 V1.21 完全一致；持久化为 opt-in。新增依赖均为 provided + optional。
- **可演示价值**：`store=jdbc` 后，一次 `POST /api/admin/skills` 注册 + 一次 `rollback`，**重启进程再查** `/api/admin/skills`，版本与灰度状态仍在——这正是企业 JD 里「版本管理 + 灰度 + 回滚」的完整闭环。
- **V1.23 候选**：
  1. 灰度与 ToolScope 联动（按版本声明 scope，灰度流量携带对应权限）；
  2. Skill Registry 与 ToolRegistry 双向同步（注册 Skill 即注册工具）；
  3. 多副本一致性（乐观锁 / 版本号 CAS，或接入 Redis 广播刷新）；
  4. mcp.so / Glama 注册表提交（Skill Registry + Signed Card 打标）。
